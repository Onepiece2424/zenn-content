## はじめに

ある日、ECR のリポジトリを眺めていたら、見覚えのない **タグなしのイメージ** が増えていることに気づきました。サイズは約 0.01MB。心当たりのないイメージが勝手に増えていると、少し不安になります。

調べてみると、これは Docker のビルド時に自動生成される **Provenance attestation** というメタデータの実体でした。この記事では、Provenance attestation とは何か、なぜ ECR に謎のイメージとして現れるのか、そして必要に応じて無効化する方法をまとめます。

## Provenance attestation とは

Provenance attestation は、コンテナイメージが **「どこで・どのように・どんな条件でビルドされたか」** を記録した来歴（provenance = 出所・来歴）の証明メタデータです。

これは **SLSA（Supply chain Levels for Software Artifacts）** というソフトウェアサプライチェーンセキュリティのフレームワークに基づいて生成されます。記録される主な内容は次のとおりです。

- ビルドのタイムスタンプ
- ビルドのパラメータや環境変数
- ソースコードやバージョン管理のメタデータ（コミットハッシュなど）

目的は、イメージの改ざん検知やビルド過程の検証を可能にし、**ソフトウェアの信頼性を担保する** ことにあります。「このイメージは確かにこのソースコードから、この CI 環境でビルドされた」ということを後から証明できるわけです。

## なぜ ECR に謎のイメージとして現れるのか

きっかけは Docker Buildx のアップデートです。

- **Docker Buildx v0.10 以降**
- **`docker/build-push-action` v4 以降**

これらのバージョンから、**Provenance attestation の生成がデフォルトで有効** になりました。そのため、意図せず attestation が作られている、というケースが多いです。

ここで重要なのが、attestation は **イメージ本体とは別の独立したコンテナイメージ** として保存されるという点です。結果として、ECR には以下のように複数のオブジェクトが並びます。

- Image Index（マニフェストリスト）
- イメージ本体
- Provenance attestation（← タグなし・約 0.01MB の「謎のイメージ」）

これが、リポジトリに突然現れる小さなタグなしイメージの正体です。マルチプラットフォームビルドの有無とは関係なく、attestation を生成するかどうかだけが原因になっています。

## 実害：Lambda などでデプロイエラーになることがある

見た目が気持ち悪いだけならまだ良いのですが、実害が出るケースもあります。

イメージが Image Index・本体・attestation に分かれることで、一部のサービスがマニフェストを解釈できず、デプロイに失敗することがあります。特に **AWS Lambda のコンテナイメージデプロイ** で、次のようなエラーに遭遇することがあります。

> The image manifest or media type is not supported.

Lambda 側が attestation 付きのマルチマニフェスト構成に対応していないことが原因です。「ビルドは通るのにデプロイだけ失敗する」という状況にハマると、原因の特定に時間がかかりがちなので注意してください。

また、Amazon Inspector のイメージスキャンはイメージ数を単位に課金されるため、attestation の分だけスキャン対象が増え、わずかながらコストにも影響します。

## Provenance attestation を無効化する方法

サプライチェーンの検証が不要で、上記のような不都合だけが気になる場合は、attestation の生成を無効化できます。用途に応じて次のいずれかを設定してください。

### GitHub Actions（build-push-action）の場合

`provenance: false` を追加します。

```yaml
- name: Build and Push
  uses: docker/build-push-action@v5
  with:
    push: true
    provenance: false   # ← これを追加
    tags: ${{ steps.meta.outputs.tags }}
```

### docker build コマンドの場合

```bash
docker build --provenance=false -t my-app .
```

### docker compose build の場合

環境変数で一括無効化できます。

```bash
export BUILDX_NO_DEFAULT_ATTESTATIONS=1
docker compose build
```

## 無効化すべきか、残すべきか

無効化ありきではなく、目的に応じて判断するのがおすすめです。

**無効化を検討すべきケース**

- ECR に余計なタグなしイメージを残したくない
- Lambda などデプロイ先が attestation 付きマニフェストに未対応
- Inspector のスキャン対象・コストを最小限にしたい

**残しておくべきケース**

- ソフトウェアサプライチェーンの検証・監査が求められる
- ビルドの来歴を証明できる状態を保ちたい

セキュリティ要件がある環境ではむしろ積極的に活用したい機能なので、「消せばいい」ではなく「なぜ生成されているか」を理解した上で判断するのが大切です。

## まとめ

- ECR に現れるタグなしの約 0.01MB イメージの正体は **Provenance attestation**（ビルドの来歴証明メタデータ）
- Docker Buildx v0.10 / `build-push-action` v4 以降で **デフォルト有効** になったのが原因
- attestation は独立したイメージとして保存されるため、**Lambda などでデプロイエラー** を起こすことがある
- 不要なら `provenance: false` や `BUILDX_NO_DEFAULT_ATTESTATIONS=1` で無効化できる
- ただしサプライチェーンセキュリティの観点では有用な機能なので、目的に応じて残すか判断する

謎のイメージに気づいたら、まずは「これは attestation では？」と疑ってみると原因の切り分けが早くなります。
